### P0-1 增量同步清空未变更文件的分块 —— **已修复，成立**

**构造**：真库造 1 个上传文档 + 3 个真实文件（`a.md`/`b.md`/`c.md`，内容量不同以便区分），全量摄取 → 记录每文件分块数 → **只改 `a.md`** → 增量同步 → 断言 `b.md`/`c.md` 块数与内容不变 → **再同步一次（全未变更）** → 断言块数完全不变。

**实测输出**：
```

仅改 a.md 同步后每文件分块数: map[a.md:3 b.md:3 c.md:1]
全未变更同步后每文件分块数:   map[a.md:3 b.md:3 c.md:1]
--- PASS: TestQA_P0_1_IncrementalSyncKeepsUnchangedFileChunks (0.17s)
```
- `b.md` 3→3、`c.md` 1→1：未变更文件分块**未被清空**（旧实现会整篇 DELETE）。

**结论**：P0-1 真修复。分块保留粒度正确到"文件级"，不是"文档级"。

这是真正的高风险点：若清理逻辑漏掉重复行，建唯一索引会直接失败导致升级中断。在 `qa_mig2` 上先迁到 version 5，造"同文档 3 条排队/运行中任务 + 另一文档 1 条历史失败任务"，再迁到 6：

```

 id | document_id | status
  1 |           1 |      1
  2 |           1 |      2
  3 |           1 |      2
  4 |           2 |      4      <- 历史失败任务，不应被碰

GOTO OK version=6 dirty=false

-- 迁移后
1|1|1|-                                            <- 保留 id 最小的一条
2|1|4|迁移前清理：运行中任务重复                      <- 置失败并带可识别的 error 文案
3|1|4|迁移前清理：运行中任务重复
4|2|4|历史失败                                     <- 未被波及
```

```

DETAIL: 键值"(document_id)=(1)" 已经存在
```
**结论**：数据清理逻辑正确（保留最小 id、置失败并留痕、不波及其它文档的已结束任务），唯一索引真实拦截并发双任务（P1-10 的 DB 兜底成立）。

## 5. 高风险改动逐条审查

### 5-1 AUTH_007 强制改密的路由覆盖与中间件顺序 —— **通过**

`internal/handler/router.go`：
- `authed`（Auth + 全局限流）下**只有** `POST /auth/password` 一条直挂路由，且它是白名单内的改密接口——无其它业务路由绕过 `mustChangeOK`。
- 所有业务路由（kbs / kb / members / search / conversations / documents / messages）都挂在 `mustChangeOK := authed.Group("", RequirePasswordChanged())` 之下（`router.go:97,107,150-157`）。
- admin 组顺序为 `Auth → 限流 → Admin → RequirePasswordChanged`（`router.go:164-169`）：**无权限者先拿到 403 FORBIDDEN，不会泄露"该账号处于待改密状态"**；管理员若被标记改密，仍被 AUTH_007 挡在业务接口外，但改密接口在 `authed` 组内可正常调用，不会自锁。
- 白名单以 `"METHOD 完整路径"` 精确匹配（`middleware/auth.go:80-88`），`/healthz`、`/readyz` 公开可达。
- 端到端佐证：`internal/integration/m2_kb_test.go` 新增断言——管理员建号后首登响应 `must_change_password=true`，未改密访问 `GET /kbs` → **403 AUTH_007**，改密后放行。

**观察（非阻塞）**：`/auth/me`、`/auth/logout` 在白名单内但**路由未实现**（当前 404）。白名单比路由宽是防未来遗漏的合理取舍，已在该文件注释说明。

### 5-2 credential 契约（`{kind,secret}` ↔ 裸字符串）与 SSH host key —— **通过**

## 8. 新增问题（本次验收发现，均非"P0 未修复/迁移链断裂/断言放宽"）

### 8-1 【P1】`WORKER_ID` 跨重启变化会导致文档**永久卡死且无用户侧恢复入口**

- **位置**：`internal/repo/document.go:323-348`（`FailZombieTasks` 的新条件） + `internal/config`（`DefaultWorkerID()` 缺省取 hostname）
- **触发条件**：worker 在摄取过程中崩溃/被 kill；重启后 `WORKER_ID` 与崩溃前**不同**。缺省取主机名时，**k8s 每次重建 Pod 主机名必变**，因此该场景在 k8s 上是常态而非边缘。
- **机制**：新实例执行 `FailZombieTasks("pod-bbb")`，判定条件为 `(worker_id='pod-bbb' AND status IN(1,2)) OR (worker_id IS NULL AND status=2)`。上一实例遗留的行是 `worker_id='pod-aaa' AND status=2`，**两段都不命中** → 任务永远停在 running，文档永远停在 `status=2(处理中)`。
- **用户侧后果**：无任何恢复入口——
  - `Retry` 要求 `status=4`（失败）→ 返回 `VALIDATION_FAILED（仅失败状态的文档可重试）`；
  - `Reindex` 要求 `status=3`（就绪）→ 拒绝；
  - `Sync` 对处理中文档直接拒绝，且仅支持 git 类型。
  - 同时 `uq_ingest_tasks_running`（`document_id` 部分唯一索引）也**不允许插入新任务**。
  - 唯一出路是删除文档重建（上传文档需重新上传、git 文档需重新配置凭证）。
- **实测证据**（`internal/qa_probe`，需 `QA_EXPECT_KNOWN_BUGS=1`）：
  ```
  新实例恢复后：任务 status=2 worker_id=pod-aaa；文档 status=2
  文档 retry 返回: VALIDATION_FAILED（仅失败状态的文档可重试）
  【缺陷确认】worker_id 变化后，上一实例的 running 任务未被回收…
  ```
- **定性**：这是 P1-8 修复**引入的新失败模式**——旧实现是"过度清理"（会杀掉别的实例，但可自愈）；新实现是"清理不到"（不误伤别人，但自己留下的残骸永久占位）。属于**可用性回归**，不涉及数据损坏与安全。
- **建议修法（择一）**：
  1. 在 `FailZombieTasks` 的"无归属"分支补一条**租约**条件：`OR (status = 2 AND started_at < now() - interval '10 minutes')`，覆盖"归属陈旧"的残留（审计原本就建议过 lease/heartbeat）；
  2. 或允许 `Retry/Reindex` 在"文档处理中且最近无心跳"时强制回收僵尸任务；
  3. 至少：在 `.env.example` 明确写"`WORKER_ID` 必须**跨重启稳定**（k8s 请用 StatefulSet 序号或显式配置，勿依赖缺省主机名）"，并在启动日志打印当前 `worker_id` 以便排障。
- **是否阻塞合并**：不阻塞，但**必须**作为已知问题 + 部署要求写入交付说明（见 §0 合并条件 1）。

### 8-2 【P1（窄口径）】增量同步中"文件被改成切不出块"时旧分块永久残留

- **位置**：`internal/worker/pipeline.go:413-418`（`embedAndStore` 的 `len(flat) == 0` 早退）
- **触发条件**：某文件内容变更后 `rag.Chunk` 产出 0 块（典型：用户把文件**清空**），**且本轮没有其它文件产出分块**。
- **机制**：`buildChunks` 已把新 `content_hash` 写入 `document_files`，但 `groups` 中该组 `chunks` 为空；`embedAndStore` 见 `len(flat)==0` 便当作"本轮无变更文件"直接 `return nil`（注释也写的是"本轮无变更文件"），**`DeleteChunksByFile` 从未执行**。由于 `content_hash` 已更新，**后续任何 sync 都不会再处理该文件** → 旧分块永久残留。
- **后果**：该文件已不存在的内容仍留在 `chunks` 表，会被检索/引用命中，前端展示已删除的片段 → 错误引用（影响 PRD R5 引用可信度）。
- **实测证据**（`internal/qa_probe`，需 `QA_EXPECT_KNOWN_BUGS=1`）：
  ```
  a.md 清空后分块数: before=2 after=2
  【缺陷确认】a.md 已被清空，但旧分块仍残留 2 条 …
  ```
- **影响面**：比 8-1 窄（需要"本轮所有变更文件都切不出块"），且需用户主动清空文件。故定为窄口径 P1 / 临界 P2。
- **建议修法**：把 `len(flat)==0` 的早退改为按 `isSync` 区分——`isSync` 时仍遍历 `groups` 执行 `DeleteChunksByFile`（空组即清理），只有 `groups` 本身为空（本轮确实无变更文件）才早退。约 3 行改动，补一个用例即可。

### 8-3 【P2】`ParseCredential` 对"JSON 合法但 kind 非法"的输入回落为 token

见 §5-2 观察。实际不可达（写入前已校验），仅作健壮性建议。

### 8-4 【P2】`SetAdmin` 在"实际无变化"时也 bump `token_version`

`internal/service/user_admin.go:176-181`：即使 `makeAdmin == target.IsAdmin`（重复设/重复撤同一状态）也会 `TokenVersion++`，导致该用户被无谓登出。语义保守但会误踢会话。建议仅在 `target.IsAdmin != makeAdmin` 时 bump（对比 `SetStatus` 也需注意同理）。

### 8-5 【P2】`CreateUpload` 部分成功时丢弃已建文档的返回

见 §5-5。第 N 个文件失败 → 前 N-1 个已落库/落盘且已入队，但接口返回错误、不返回 items。建议整批原子或返回"部分成功清单"。
