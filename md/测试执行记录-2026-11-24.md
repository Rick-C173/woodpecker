### 7.1 【P0 已复现】增量同步清空分块（数据丢失）

探针：`internal/worker/probe_sync_test.go :: TestProbeSyncWipesChunks / TestProbeSyncPartialChange`（真 `repo.DocumentRepo` + 真 Pipeline）

**场景 A：所有文件都没改，跑一次 sync**

```
【全量摄取后】分块数 = 5
【增量同步后】分块数 = 0
【同步后文档状态】status = 3（DocStatusReady=3）
❌ P0 复现：增量同步清空了分块。同步前 5 条 → 同步后 0 条（丢了 5 条）
❌ 更糟：分块已全部丢失，文档状态仍为 ready（静默数据丢失）
```

**场景 B：只改 a.md，b.md 未动**

```
【全量后按文件分块】[{FilePath:a.md N:2} {FilePath:b.md N:2}]
【仅改 a.md 后按文件分块】[{FilePath:a.md N:2}]
❌ b.md 内容未变却丢了全部分块（库里只剩 a.md 的分块）
```

**根因链**（已核对到行）：
1. `internal/worker/pipeline.go:311-314`：未变更文件 `continue`，**不产出 chunk，也不删自己的旧分块**（这一步是对的）
2. `pipeline.go:170` → `embedAndStore(ctx, d, chunks)`，`chunks` 只含**变更/新增文件**的分块；全未变时 `chunks == nil`
3. `pipeline.go:363-364` / `:390` → 无条件调 `p.docs.ReplaceChunks(ctx, d.ID, chunks)`
4. `internal/repo/document.go:164-186` → `ReplaceChunks` 语义是**整文档先 `DELETE FROM chunks WHERE document_id=?` 再插入**
5. `pipeline.go:182` → 之后仍把 `d.Status` 置 `DocStatusReady`

所以"跳过未变更文件"反而成了破坏性操作：**增量同步每次都把未变更文件的分块删掉，且对外表现为成功**。直接违反开发计划 M4 验收"同步只处理变更文件"与文档详情页"文件清单/分块"的一致性。

**为什么 209 个测试全绿却没发现**：`internal/testutil/doc_fake.go:198-205` 的 `FakeDocRepo.ReplaceChunks` 是**空实现**，注释写着"分块不落内存（pipeline 断言经由 embedder/清单验证）"；同时 `grep -c "Sync|isSync" internal/worker/pipeline_test.go` = **0**，`worker` 包**根本没有 sync 用例**。缺陷被替身的空实现彻底掩盖。

### 7.2 【P0 已复现】SSE 中断不落库——原单测是假通过

**(a) 先证明原测试假通过**：在副本里把 `internal/service/chat_test.go:110` 的替身改成"像 `database/sql` 一样尊重 ctx"（`ctx.Err() != nil` 就返回错误），**一行测试代码都没改**，原测试立刻变红：

```
  "[{1 1 1 问题 false ...}]" should have 2 item(s), but has 1
```

只剩用户提问（1 条），assistant 的部分回答根本没落库。原测试之所以绿，纯粹因为 `func (f *fakeConvStore) CreateMessage(_ context.Context, ...)` **把 ctx 丢掉了**。

**(b) 再证明真库行为一致**：探针 `internal/probe/probe_test.go :: TestProbeCancelledCtxBlocksSave`（真 `repo.ConversationRepo` + 真库）

```
【已取消 ctx 下 CreateMessage 的返回】err = context canceled

✅ 对照：换成未取消 ctx 后写入成功 —— 说明失败原因确为 ctx 取消，而非数据问题
```

**根因链**：`service/chat.go:419` `interrupted := ctx.Err() != nil` 判断对了，但 `:448` `s.store.CreateMessage(ctx, m)`、`:452` `s.store.ReplaceCitations(ctx, m.ID, ...)`（以及 regenerate 路径 `:423/:433/:437`）仍用**同一个已取消的 ctx**；`repo/conversation.go:66` `dbx(ctx) = r.db.WithContext(ctx)` → 写入必然返回 `context canceled` → 部分回答丢失、`interrupted` 永远到不了库。

### 7.3 【P0 已复现】最后一个管理员保护可绕过（后台永久锁死）

探针：`internal/probe/probe_test.go :: TestProbeLastAdminBypass`（真库 + 真 `UserAdminService`）

```
【禁用后 B】status=2 is_admin=true
【撤销 A 的管理员权限】err = <nil>          ← 应返回 USER_003
【实际情况】is_admin=true 共 1 人；其中 status=1（可用）0 人
❌ 复现成功：撤销 A 返回 nil，此后系统可用管理员 = 0（后台永久锁死）
```

**根因**：`internal/repo/user.go:30-34` `CountAdmins` 是 `WHERE is_admin = true`，**不过滤 `status`**；`internal/service/user_admin.go:164-171` 用它的返回值判断"是否最后一个管理员"。而"禁用"（`SetStatus`）只改 `status`、**保留 `is_admin=true`**，所以被禁用的管理员仍被计数 → 保护被绕过 → 撤销唯一可用管理员后，系统 0 个可用管理员，且**再无入口恢复**（只能改库）。

**附带问题（同一处，已核对）**：`SetAdmin` 撤权时**不 bump `token_version`**（`user_admin.go:173-177` 只改 `IsAdmin` 后 `Save`），而对比 `SetStatus` 禁用时**有** `target.TokenVersion++`（`user_admin.go:135`）。`jwt.go:32` 把 `adm` 写进 claims，`middleware/auth.go:47` 直接信任 claims 的 `IsAdmin`（`:53-58` `Admin()` 只看 `CtxIsAdmin`）——所以**被撤销管理员的旧 token 在整个 TTL（默认 24h）内仍拥有管理员权限**。

### 7.4 【P2 已复现】Git 凭证放在 username 位置（平台相关）

探针：`internal/probe/probe_git_test.go`（用假 git-http 服务捕获 `Authorization` 头）

```
【服务端收到的 Authorization】"Basic TVlUT0tFTjEyMzo="
【解码后 user:pass】"MYTOKEN123:"
```

`internal/rag/fetch.go:74` `githttp.BasicAuth{Username: credential, Password: ""}` 实际发送 `base64(token + ":")`，即**token 当用户名、密码为空**。

严重级别需按平台区分（这点与 Engineer 的判断略有出入，如实记录）：
- **GitHub / Bitbucket**：接受 token 作 username（官方文档示例就是 `https://<token>@github.com/...`），**能用**
- **GitLab Personal Access Token**：要求 `oauth2:<token>`，token-as-username **必定 401** → 表现为 `DOC_003` 仓库不可达

结合 §4.4（`FetchGit` 覆盖率 0%，从未被执行），这条路径**在任何平台上都没有被验证过**，无论凭证位置对错都无人知晓。
