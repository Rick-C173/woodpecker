## 2. 结论摘要

**一句话结论**：架构分层与安全基座（JWT+token_version、argon2id、R6 中间件链、AES-GCM、真库集成测试脚手架）质量偏高，数据库 DDL 与设计文档的 15 张表/15 个索引**完全一致**；但存在 **3 个 P0**（P0-1：任何一次增量同步都会让未变更文件的内容从检索中消失且状态仍显示「已就绪」；P0-2：SSE 中断后部分回答不落库；P0-3：最后管理员保护可绕过，系统可被锁死到 0 个可用管理员）、**15 项 P1**（撤管理员不失效 token、首登强制改密未在服务端强制、默认密钥可启动、SSH 凭证路径完全未实现、时间格式不符合 RFC3339 约定、契约/文档与实现多处漂移等）、**37 项 P2**（其中 P2-37「测试替身结构性盲区」独立成节，见 §3.4），`开发计划` 中 M4/M5/M6/M7 的「已勾选 + 验收通过」有若干项与代码实际能力不符。

### 3.4 测试盲区（P2-37，本轮最重要的过程性发现）

> 209 个用例全绿、lint 0 issues、`-race` 通过，但三个 P0 全部从测试网里漏了过去。根因不在"写得少"，而在**替身（fake）的结构性缺陷让某些缺陷类别原理上不可测**。四条，逐条带证据：

1. **删除型缺陷测不出**：`internal/testutil/doc_fake.go:198-205` 的 `FakeDocRepo.ReplaceChunks` 把三个参数全部 `_` 掉、直接 `return nil`（注释还写着「分块不落内存」）。任何「先删后插」被写成「只删不插」的缺陷，在单测里表现为零差异 → **正是 P0-1（同步清空分块）逃逸的原因**。
2. **取消/超时路径假通过**：`internal/service/chat_test.go:110` 的 `fakeConvStore.CreateMessage(_ context.Context, …)` 忽略 ctx。QA 只把这一处改成「`ctx.Err() != nil` 就返回错误」、测试代码一行未动，`TestAskInterruptedSavesPartial`(`:501-523`) 立刻变红（`should have 2 item(s), but has 1`）→ **正是 P0-2（SSE 中断不落库）逃逸的原因**。
3. **状态组合类缺陷测不出**：没有任何用例构造「禁用 × 撤权」的组合态（禁用保留 `is_admin=true` + `CountAdmins` 不过滤 status）→ **正是 P0-3（系统锁死）逃逸的原因**。
4. **整块功能零用例**：`internal/worker/pipeline_test.go` **无任何 sync 用例**（grep `Sync|isSync` 零命中）；`rag.FetchGit` 覆盖率 **0%**；`internal/worker/worker.go` 的 `NewClient / EnqueueIngest / EnqueueContext / Close / NewServer / Run / handleIngest` **7 个函数全 0%** —— 只有 `pipeline.Process` 的 71.4%，只证明"拿到任务后怎么处理"，没证明"任务能投递、能取出、能分发"。

**另有两处"假绿"入口**（QA 实测）：
- `internal/repo/it_setup_test.go:35-38` 用 `os.Exit(0)` 跳过集成测试：把 `TEST_DSN` 指向死端口时，`go test` 返回 **`ok`、exit 0、RUN=0 且无任何 SKIP 行**，9 个仓储用例无声消失而 CI 全绿（`internal/integration` 用 `t.Skipf`，口径不一致）。应改 `log.Fatalf`，或统一到 testutil 的一个 `SkipOrFail(t)`。

## 5. 值得肯定的设计

1. **`token_version` 失效模型干净**：`middlaware/auth.go:33-45` 只查一次 DB 就同时解决「禁用立即生效」「改密踢出」「删除即失效」，没有引入黑名单/Redis 会话，代价与收益匹配（唯一缺口是 P1-2 的 `adm` claim）。
2. **密码与密钥基座正确**：argon2id 参数取 OWASP 推荐（`crypto/password.go:17-23`，m=64MB/t=3/p=2）、`subtle.ConstantTimeCompare`、随机 salt、`RandomPassword` 去易混字符；AES-GCM 每次随机 nonce 并以 `nonce||ct` 落库（`crypto/aesgcm.go:37-43`），无 nonce 复用风险。
3. **R6 中间件链的「不可见原则」落实到位**：`middleware/kb.go:29-59` 用「非成员 → 404」而非 403，且 `KBAccess` 在所有 `/kbs/:kb` 子路由上都是第一环；`service/document.go:431-443`(`getOwned`)、`service/chat.go:140-162`(`canAccess`) 在两处再次做「归属校验防越权调用」，IDOR 面基本堵死（未发现真实越权）。
4. **`ReplaceChunks` 用「事务内先删后插」实现重索引的原子替换**：`repo/document.go:164-186` 在 MVCC 下让读请求只看旧快照、提交后原子切换，恰好满足「重建期间问答不受影响」——这是 P0-1 修好后应当保留的核心机制。
5. **测试与工程纪律**：真库集成测试用 `TEST_DSN` 注入、CI 分离 lint/vet/build/单测/集成（`-p 1` 串行）、`cgo-smoke` 提前验证 tree-sitter 风险、`.golangci.yml` 开 24 个 linter（含 `bodyclose`/`errorlint`/`noctx`）、`-race` 通过——这套约束明显降低了低级缺陷率。**但须加限定**：替身层存在系统性盲区（`FakeDocRepo.ReplaceChunks` 空实现、fake 忽略 ctx、`it_setup_test.go:35` 用 `os.Exit(0)` 让集成用例无声消失），使 P0-1/P0-2/P1-3 在 209 个全绿用例下全部漏网（见 P2-37）。脚手架是好的，替身的「可失败性」是短板。
